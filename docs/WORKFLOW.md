# Workflow

## 목적

이 문서는 AI 에이전트가 task를 진행할 때 따라야 할 작업 순서, 진행 제약, 상태 관리 규칙을 정의합니다.

## 문서 우선순위

문서 해석 우선순위는 아래와 같습니다.

1. 사용자 직접 요청
2. 현재 진행 중인 task 문서
3. `docs/PLANS.md`
4. 나머지 프로젝트 문서

문서끼리 충돌하거나 현재 저장소 상태와 맞지 않으면, 구현 전에 불일치를 먼저 보고하고 수정 범위를 제안합니다.

## 작업 흐름

사용자가 task 초안을 기반으로 진행을 요청하면 아래 순서로 작업합니다.

1. 관련 task와 선행 산출물을 확인합니다.
2. `docs/PLANS.md`에서 현재 단계 상태를 확인하고 작업 시작 시 `진행중`으로 갱신합니다.
3. `docs/ARCHITECTURE.md`의 폴더 책임과 화면 파일 이름 원칙을 확인합니다.
4. 관련 코드와 현재 화면 구조를 읽습니다. 관련 코드가 아직 없으면 이 단계는 건너뜁니다.
5. 코드 수정 전 `docs/ARCHITECTURE.md`와 `docs/STYLEGUIDE.md` 기준으로 아래 항목을 확인합니다. 해당되면 구현 전에 사용자에게 먼저 제안합니다.
- 같은 성격의 공용 로직이 실제로 2곳 이상에서 반복되는지
- 파일 책임이 과도하게 누적되는지
6. 필요한 코드 변경을 구현합니다.
7. 구현 후 `docs/TASK_WRITING.md`의 작성 규칙에 맞춰 task 문서를 실제 코드 기준으로 갱신합니다.
8. `docs/TESTING.md`의 현재 실행 확인 모드에 따라 확인을 진행합니다.
9. 사용자에게 필요한 수동 작업 또는 결과 확인을 요청합니다.
10. 결과 확인이 끝나면 `docs/PLANS.md`의 `최근 작업 로그` 줄 수를 확인하고, 20줄 이상이면 `작업 로그 관리` 규칙에 따라 `docs/LOGS.md`로 이관합니다.
11. 확인이 완료된 뒤 task 문서와 `docs/PLANS.md`에서 현재 단계 상태를 `완료`로 갱신합니다.

## 진행 제약

- 구현은 task 구현 항목에 명시된 것만 합니다. 범위 밖 항목은 구현하지 않습니다.
- task 문서 작성과 갱신은 승인 없이 진행합니다.
- task 문서 이외의 파일 변경은 적용 전에 변경 요약을 제시하고, 사용자 승인을 받은 뒤 진행합니다. 단, 새로운 task 문서 작성시 `docs/PLANS.md` 파일 갱신은 승인 없이 진행합니다.
- `.env` 파일의 실제 API 키 값은 읽거나 출력하지 않습니다.
- 결과 확인이 끝나기 전에는 다음 단계로 넘어가지 않습니다.
- 구현과 문서 갱신은 같은 작업 흐름 안에서 함께 반영합니다.

## 상태 관리 원칙

- 단계 상태는 `예정`, `진행중`, `완료`, `차단됨`만 사용합니다.
- 최근 작업 로그에는 구현, 실행 확인, 결과 확인 결과를 남깁니다.

## 작업 로그 관리

- `docs/PLANS.md`의 `최근 작업 로그`는 최신 진행 상황 확인용으로 유지합니다.
- `docs/PLANS.md`의 `최근 작업 로그`가 20줄 이상이 되면, 작업 중인 에이전트는 가장 오래된 15줄을 `docs/LOGS.md`로 이동하고 최신 5줄만 남깁니다.
- 이동한 로그는 삭제하지 않고 `docs/LOGS.md`에 유지합니다.
